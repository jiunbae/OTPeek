# Windows 출시 준비 후속 검증

**후속 갱신:** 아래 artifact/실행은 당시 이력이다. 현재 최종 preview와 runtime·리소스 보완 상태는 [SELF_CONTAINED_QA_20261025.md](SELF_CONTAINED_QA_20261025.md), WACK 원인 분석은 [WACK_FINDINGS_20261025.md](WACK_FINDINGS_20261025.md)를 따른다. Android 클립보드 정책 선택 대기는 사용자 위임으로 해소됐다.

2026-10-25에 기존 차단 상태를 실제로 다시 확인하고 Windows 클립보드 서비스의 보안·동작 문제를 수정했다. 기존 Android/Rust/Windows fixture 결과는 반복 실행하지 않았다. 이번 산출물도 **placeholder identity의 로컬 preview이며 제출·출시 완료가 아니다**.

**후속 갱신:** 사용자의 jiun 계정 사용 지시로 설치·UI·COM·WACK를 실제 실행했고, 정확한 widget card 누락도 추가 수정했다. 아래 preview와 desktop 로그인 차단 기록은 그 이전 이력이다. [최신 데스크톱 검증과 artifact](DESKTOP_QA_20261025.md)를 기준으로 확인한다. `jiun-test` 로그인은 더 이상 전제 조건이 아니다.

## 수정과 실제 검증

[ClipboardService](../../windows/Otpeek.Core.Windows/Services/ClipboardService.cs)는 기존에 `IsFromRoamingClipboard`라는 사용자 속성을 넣고 일반 SetContent를 호출했다. 이 속성만으로 history/roaming 차단을 보장할 수 없었다. 현재는 Windows 공식 `Clipboard.SetContentWithOptions`에 `IsAllowedInHistory=false`, `IsRoamable=false`를 전달하며, 반환값 false를 복사 성공으로 처리하지 않는다. 이 API는 Windows 10 1809부터 지원되어 앱의 최소 버전 19041보다 낮다. [Microsoft 공식 API](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.datatransfer.clipboard.setcontentwithoptions?view=winrt-22000).

자동 삭제는 기존에 현재 clipboard를 무조건 지웠다. 이제 복사별 임의 소유 표식을 넣고 현재 항목과 일치할 때만 지운다. 다른 앱이 동일한 문자열을 복사해도 표식이 없으면 보존한다. 이전 timer는 자신이 생성될 때의 소유 표식을 확인하므로 새 복사를 지우지 않는다. 자동 삭제 시간의 기본값·사용자 설정, Flush 동작과 Android의 미결정 정책은 바꾸지 않았다.

[클립보드 fixture](../../tests/Otpeek.Clipboard.Fixtures/README.md)는 실제 패키지 assembly와 실제 WinRT DataPackage/ClipboardContentOptions를 사용하고, 시스템 clipboard 접근 함수만 메모리 transport로 교체한다. **11개 assertion 통과**: 복사 전 미접근, history/roaming 옵션, flush/read, 소유 항목 명시 삭제, 타 앱의 같은 문자열 보존, 교체 후 만료, 새 복사에 의한 timer 취소, 소유 항목 만료 삭제, 명시 timer 취소, 실패 반환 처리와 소유권 미획득. 사용자의 실제 clipboard는 읽거나 변경하지 않았다. 근거: `.tools/msstore/evidence/clipboard-fixtures.log` 및 Windows 작업 경로의 동일 로그.

OS의 읽기와 Clear는 원자적 compare-and-clear가 아니므로, 다른 프로세스가 검사 직후 바꾸는 경합까지 완전히 막지는 못한다. 프로세스 종료나 OS의 background clipboard 접근 거부 때 예약 삭제도 보장하지 않는다. 별도 Win32 **위젯 복사 경로**는 이번 수정 대상이 아니며, 실제 history/roaming·데스크톱 UI 검증과 함께 구분해야 한다.

## 최신 preview

- x64 Release StoreUpload 재빌드 **오류 0**, 42.27초. 근거 `package-build-clipboard.log`.
- 실제 upload envelope의 embedded package **1개**를 SDK MakeAppx unbundle/unpack으로 검증했다. 이번 내부 package count를 이전 4개 기록과 혼동하지 않는다. 최종 app manifest Resources는 기존 고지 포함 preview와 동일한 `EN-US`, scale200이다. 한국어 Store localization 검증을 이 결과로 주장하지 않는다.
- 앱·Rust·위젯 필수 payload/등록/PE 아키텍처/preview identity 검사 통과. 고지 210개 package에 연결된 원문 및 원본 crate 해시도 유지됐다.
- Rust DLL과 managed UniFFI DLL은 이전 고지 포함 preview와 byte-identical임을 확인했다. 변경 없는 crypto/FFI/RFC 검사를 반복하지 않았다.
- 파일 크기 **57,243,006 bytes**, SHA-256 `05b2820631d305bb350cfa947041bc842cf4dff0e216b32931431eea13f00439`.
- 로컬 파일 `.tools/msstore/artifacts/OTPeek-2.0.1.0-x64-PREVIEW-20261025.msixupload`.

기존 Rust 코어 source/API/암호화 포맷, Store identity, 실제 사용자 vault/키/앱 등록, 원본 worktree와 다른 프로젝트를 수정하지 않았다. 개인 desktop의 clipboard를 시험하지 않았다.

## 현재도 남은 실제 사용자 단계

`jiun-home` 접속은 정상이다. `quser` 재확인 결과 활성 desktop은 개인 사용자 `jiun`뿐이며 전용 `jiun-test`는 로그인돼 있지 않다. WACK 실행 파일의 `/?` 도움말과 `querytestids`는 읽기 전용으로 확인했고, 실제 WACK test/reset/install은 실행하지 않았다. 테스트 ID를 얻었다는 사실을 WACK 통과로 표시하지 않는다. 전용 fixture desktop 로그인 후 설치·UI·widget COM·OS clipboard·업데이트·WACK 검증이 필요하다.

Partner Center는 새 Browser runtime 연결을 다시 시도했으나 `browser-service.mjs`의 이전 버전 경로를 찾지 못하는 오류가 그대로였다. 별도로 기존 signed Tacto Helper의 Safari 읽기도 `window_list_unavailable`, AX `-25204`로 실패했다. 인증 상태는 알 수 없으며 쿠키·프로필·비밀번호·토큰을 읽지 않았다. 재설치나 Safari 강제 재시작도 하지 않았다. **OTPeek의 공개 Identity Name, Publisher, PublisherDisplayName와 기존 Store 버전**을 전달받거나 Partner Center 창/지원 브라우저 연결이 복구돼야 실제 앱 연결을 진행할 수 있다.

Android의 클립보드 즉시 삭제 대 최대30초 정책 선택과 전용 실기기 검증, 두 스토어의 최종 운영·공개 정보는 별도 미완료다. 독립 작업의 과거 결과는 [10월 24일 Windows QA](QA_20261024.md), [Android QA](../android/QA_20261017.md)에 보존한다. 이번에 다른 세션에 지시를 재전파하거나 새 에이전트를 생성하지 않았다.
