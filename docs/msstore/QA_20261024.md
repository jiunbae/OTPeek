# OTPeek Microsoft Store 빌드 검증

2026-10-24 전체 작업 대조 결과, Android 로컬 MVP/기존 에뮬레이터 QA와 디스크 정리는 완료됐으나 Microsoft Store 빌드·제출은 완료되지 않은 상태였다. 이번에는 복구된 Windows 머신에서 실제 패키징 문제를 수정하고 최종 x64 preview upload를 검증했다. **Store 제출·게시 완료를 의미하지 않는다.**

후속 직접 지시에 따라 Windows QR/DPAPI/quick-surface/WebDAV/sync의 신규 assertion 34개를 추가 완료했다. 고지 자료를 포함한 최신 preview는 아래 `21b75d…` 파일이며, 실행 바이너리 149개가 이전 검증본과 바이트 동일함을 확인했다. 기존 Android 검증은 반복하지 않았다.

## 환경과 격리

`jiun-home` SSH 연결이 복구됐다. Windows 11 Education `10.0.26300`, .NET SDK `10.0.402`와 .NET 8 SDK/runtime, Rust `1.96.1` MSVC, Windows SDK `26100`, Visual Studio 2022의 PDB 변환 도구를 사용했다. 새 운영 의존성·전역 도구 설치나 계정·SSH 설정 변경은 없다.

소스 기준은 이 worktree의 HEAD `54ee0bf`와 현재 미커밋 소스다. Android 도구용 UniFFI feature gate는 기본 bindgen feature를 유지한 채 Windows에서 빌드됐다. 원본 `/Users/jiun/workspace/otpeek`의 Windows 삭제 변경과 다른 worktree는 보존했다.

Windows 작업은 신규 `F:/workspace/otpeek-msstore-20261024`에만 격리했다. Calex 담당자의 기존 대화에 해당 경로의 소유권 충돌만 묻는 read-only 요청을 남겼으며 전체 사용자 지시를 재전파하거나 새 에이전트를 생성하지 않았다. 기존 `F:/workspace/calex`, `F:/workspace/OTPeek`와 실행 중인 OTPeek PID `15584`를 변경·중단하지 않았다. 최종 확인에서도 해당 프로세스는 실행 중이다.

## 수정한 빌드 문제

- **위젯 NuGet 복원 누락:** 깨끗한 checkout에서 앱 복원만 수행한 뒤 별도 위젯을 빌드해 `NETSDK1004`로 실패했다. [패키징 스크립트](../../windows/scripts/package-msix.ps1)가 각 요청 플랫폼의 위젯을 명시적으로 복원한다.
- **Store symbols 도구 탐색:** dotnet SDK에서 설치된 `mspdbcmf.exe`를 찾지 못해 심볼 패키징이 실패했다. 같은 스크립트에서 기존 VS 도구를 탐색하고 MSIX targets가 사용하는 fullpath 및 x64/x86 경로 속성을 전달한다. 심볼 생성을 끄거나 도구를 새로 설치하지 않았다.
- **위젯 payload 누락:** 빌드는 성공했으나 실제 MSIX에 위젯 exe/dll/runtimeconfig/templates가 없었다. [앱 프로젝트](../../windows/Otpeek.App/Otpeek.App.csproj)는 위젯을 빌드한 후 SDK의 AssignTargetPaths 전에 Content로 포함한다. 초기 Content 전환의 경로 중복 실패도 확인했고 root 파일별 명시 Link로 수정했다. 최종 upload에서 실제 파일·PE 아키텍처·위젯 등록을 검사했다. 제품 crypto/API/데이터 포맷과 Store identity는 변경하지 않았다.

FFI 실행은 패키지에서 추출한 managed/native DLL을 직접 지정하며 별도 UUID temp vault만 사용했다. RFC TOTP/HOTP, display/consume, 재열기 counter 유지, 백업 VMK 독립성, 잘못된 비밀번호의 파일 보존, merge/replace 계약을 확인했다. VMK·비밀번호·OTP secret을 출력하지 않고 temp vault를 제거했다. Windows 사용자 DPAPI나 실제 vault를 읽는 기존 `--diagnostics`는 실행하지 않았다.

최종 빌드 경고는 기존 ZXing/System.Drawing 관련 `MSB3277`과 Windows App SDK PRI qualifier `PRI249`다. 경고 제거를 위해 프레임워크·의존성을 임의 업그레이드하지 않았다. QR/위젯 UI 동작은 다음 격리된 설치 검증의 대상이며, FFI assertion 통과로 대신하지 않는다.

## 추가로 완료한 Windows 검증과 고지 자료

[새 Windows fixture](../../tests/Otpeek.Windows.Fixtures/README.md)는 실제 패키지의 Core.Windows/Interop/Drawing/DPAPI DLL을 참조한다. 서비스·QR 실행에서 **34개 assertion 통과**했으며 34개의 별도 단위 테스트라는 뜻은 아니다. WebDAV HTTP 사례마다 경로·fixture 인증 헤더를 확인하는 assertion 10개가 포함된다. 근거는 `evidence/windows-service-qr-fixtures.log`다.

- 독립적으로 생성한 공개 QR PNG 파일 → Windows ZXing 디코딩 → Rust URI 파서, Windows QR 생성과 BGRA 디코딩, 잘못된 프레임의 결과 없음.
- 신규 UUID temp vault와 신규 fixture VMK에만 CurrentUser DPAPI를 사용했다. 실제 quick-surface v2 reader의 즐겨찾기 정렬, v2 HOTP 제외/카운터 보존, 잘못되거나 없는 VMK의 실패 시 차단을 확인했다. default-path constructor, 기존 vault/credential 항목 및 실제 PasswordVault fallback은 호출하지 않았다.
- loopback 임시 TCP listener에서만 GET/PUT/HEAD, 암호문 보존, ETag/If-Match/If-None-Match, 404/412/401/403/503 매핑을 확인했다. Rust sync가 실제 C# WebDAV callback을 호출하고, 업로드 암호문이 같은 fixture VMK로 재열리며 HOTP counter가 유지되는지 검사했다. 외부 WebDAV 서버는 사용하지 않았다.

첫 QR harness 빌드는 Drawing 9의 공개 타입을 위한 `System.Private.Windows.Core` 참조가 빠져 실패했다. 패키지에 이미 있는 DLL을 fixture 프로젝트에서 참조하도록 고쳤으며 제품 의존성이나 프레임워크를 올리지 않았다. Windows 데스크톱은 여전히 개인 사용자 `jiun` 콘솔만 활성 상태이고 `jiun-test`는 로그인돼 있지 않았다. 기존 앱 PID `15584`와 데스크톱은 그대로 유지했다.

배포물에서 제3자 고지 파일이 없음을 확인해 [수집 도구/재현 절차](../../windows/third-party-notice-sources/README.md)를 추가했다. 복원된 NuGet 57개와 FFI의 Windows normal/build Rust graph 153개, 총 **210개 패키지**, 원문 고지 **142종**, 변경하지 않은 UniFFI/MPL crate 원본 **8개**를 `Assets/ThirdPartyNotices`에 포함했다. 빌드 전용 항목도 보수적으로 포함한 provenance이며 모든 패키지가 실행 파일에 들어갔다는 뜻은 아니다. MPL archive SHA는 Cargo.lock의 package checksum과 대조했다. upstream 보완 파일은 정확한 커밋 URL과 SHA를 남겼다.

고지 asset만 추가한 새 upload의 내부 4개 패키지를 MakeAppx로 검사했고, 포함된 모든 고지·원본 archive 해시를 확인했다. 이전 검증본의 실행 바이너리 **149개가 모두 byte-identical**하여 이전 기능 검사 결과가 그대로 적용된다. `evidence/notice-validation.json`, `notice-collection.log`, `package-build-notices.log`에 기록했다. 공개 고지·원본 crate 외에 실제 사용자 데이터·자격 증명은 넣지 않았다.

## 실제로 남은 단계

1. **Partner Center 사용자 로그인/앱 정보:** OTPeek의 Identity Name, Publisher, PublisherDisplayName, 기존 제출 버전과 앱 등록 현황이 필요하다. 다른 앱 Calex의 identity·인증서를 재사용하지 않는다. Store는 별도 계정별 앱 연결 단계이며 preview 파일을 업로드하지 않는다.
2. **Windows 전용 fixture 데스크톱:** `jiun-test` 계정이 존재·활성화돼 있고 그 프로필의 OTPeek 데이터 경로는 현재 없음을 확인했다. 기존 사용자의 앱·데이터·데스크톱과 충돌하지 않는 테스트 로그인/사용 시간을 확보한 뒤 별도 fixture identity로 설치, DPAPI 재부팅·키 손실, 앱/QR/프로토콜·파일 연결, 위젯·잠금·클립보드, 업데이트·제거, 접근성과 WACK를 실행한다. 기존 개인 사용자에서 같은 placeholder identity를 등록·교체하지 않았다.
3. **출시 정보와 범위:** 최종 운영 주체·문의처·privacy URL, 가격·시장, 지원 OS/아키텍처와 실제 기능을 [공개 초안](STORE_LISTING_DRAFT.md)에 반영한다. ARM64는 이번 x64 결과에 포함하지 않는다. 검토된 실제 제출 artifact와 자료가 갖춰진 뒤 제출 범위를 확인한다.
4. **Android 잔여 선택/조작:** [기존 QA](../android/QA_20261017.md)의 클립보드 즉시 삭제 대 최대30초 정책 선택, 전용 실기기의 생체인증·광학 QR·OEM backup·TalkBack 검증 및 최종 Play 운영 정보는 그대로 남는다. 이번 Windows 작업으로 정책을 변경하거나 재검증을 반복하지 않았다.

Partner Center의 기존 로그인 세션에서 앱 정보를 읽을 수 있는지도 직접 확인했다. `jiun-mbp`의 signed Tacto Helper로 Safari를 읽으려 했으나 `window_list_unavailable`, AX `-25204`, onscreen window count 0으로 실패했다. `tacto doctor --check`는 조작/화면 읽기 권한과 GUI 연결을 통과했고 apps 목록에도 Safari가 있었다. 로그인 안 됨·화면 잠금·권한 누락이라고 단정할 근거는 없다. 다른 작업에 영향을 줄 Safari 재시작·강제 창 열기·브라우저 대체 조작은 하지 않았다. 현재는 위 공개 앱 식별자 값을 전달받거나 실제 Partner Center 창 접근을 복구해야 한다.

후속 continue에서 `jiun-home` 데스크톱을 다시 확인했으나 활성 세션은 개인 사용자 `jiun`뿐이고 `jiun-test`는 로그인되지 않았다. Safari도 같은 AX 오류였다. 새 Browser skill의 지원 경로를 통해 Partner Center 연결을 시도했지만 runtime이 다른 버전의 `browser-service.mjs`를 찾지 못해 시작 전 실패했다. 브라우저 프로필/쿠키/토큰을 읽거나 대체 인증 경로를 사용하지 않았다.

제출 준비의 독립 작업으로 패키징 스크립트에 identity 사전 검사를 추가했다. 일반 Store 명령은 `Otpeek`/`CN=Otpeek` 등 알려진 placeholder를 복원·빌드 이전에 거부하고, 로컬 검증은 `-PreviewIdentity`를 명시해야 한다. PreviewIdentity의 다른 mode 사용도 거부한다. Windows PowerShell parser 및 두 실제 실패 경로 검증은 통과했으며, 기존 upload와 빌드는 변경/반복하지 않았다. 근거: `evidence/store-identity-guard-result.json`. 이 검사는 실제 Partner Center 등록 여부를 인증하지 않는다.

WACK CLI는 활성 사용자 세션에서 실행해야 하며 앱 배포·실행 검사를 포함한다. 해당 검증을 단순 ZIP 검사 통과로 표시하지 않는다. [Microsoft WACK 공식 절차](https://learn.microsoft.com/en-us/windows/uwp/debug-test-perf/windows-app-certification-kit).

디스크 정리의 할당 용량 기준 **620,519,424 bytes**와 보존 검사 결과는 `/Users/jiun/disk-cleanup-2026-10-24/agent-otpeek.json`에 완료 기록이 있다. 이번 빌드·증거는 그 이후 사용자 지시에 따라 별도로 생성한 것이며 이전 정리 수치에 합산하지 않는다.
